# AGENTS.md

Файл памяти для ИИ-агента, который работает с этим репозиторием.
Прочитай его целиком перед первой правкой.

Предметная область описана в `docs/pdr/0001-bronirovanie.md`: роли, гарантии,
сценарии С1 до С17 и границы объёма. Читай его, когда речь заходит о брони,
часовых поясах, ссылке-коде, отменах, валидации или о том, что входит в задачу.
Этот файл PDR не переописывает: он фиксирует устройство репозитория, порядок
работы и правила. PDR это источник истины для предметной области; спорит код,
правится код.

## 1. Что за проект

Сервис бронирования слотов на созвоны и встречи с организатором.

Организатор один раз задаёт типы встреч и часы приёма и дальше в согласовании
времени не участвует. Гость открывает страницу, видит свободное время в своём
часовом поясе и записывается сам.

Две роли, две разные модели входа:

- **Организатор.** Личный кабинет: заводит типы встреч, меняет часы приёма,
  видит список записей гостей и отменяет запись. Вход по логину и паролю.
- **Гость.** Учётной записи и пароля нет. Вводит имя и адрес почты, бронирует,
  получает подтверждение на экране. К своей встрече и к отмене его ведёт
  ссылка-код, выданная в момент брони. Почта нужна организатору как контакт.

Что сервис обязан гарантировать:

1. На один слот приходится одна действующая бронь, даже при одновременных запросах.
2. Слоты считаются на лету из расписания.
3. Время показывается в поясе того, кто смотрит.
4. После записи гость получает подтверждение, ссылку-код и файл календаря формата .ics.
5. Отмена освобождает слот; повторная отмена той же записи отклоняется.
6. Там, где записаться нельзя, приходит отказ, а не пустой ответ.

Полный набор ограничений: раздел 8 ниже и «Что осознанно не делается» в PDR.

## 2. Стек

| Слой | Технология |
|---|---|
| Язык | TypeScript в строгом режиме, Node.js 22 LTS |
| Веб-фреймворк | Fastify 5 |
| Проверка данных | Zod 4 |
| База данных | SQLite через better-sqlite3 (синхронный драйвер) |
| Контракт API | TypeSpec, из него собирается OpenAPI 3.1 |
| Интерфейс | Vite, React 19, собственный CSS без библиотек компонентов |
| Тесты | Vitest для модульных и интеграционных, Playwright для сквозных |
| Контейнер | Docker, docker compose |
| Непрерывная интеграция | GitHub Actions |

Строка этого списка не заменяется на альтернативу без решения, записанного
в `docs/adr/`. Каждая новая зависимость обосновывается одной строкой необходимости.

## 3. Где что лежит

Схема того, куда что класть. Чего ещё нет, создаёт шаг из раздела 6.

```
AGENTS.md                     этот файл
docs/pdr/                     продуктовые решения
docs/adr/                     архитектурные решения, создаётся лениво
GLOSSARY.md                   доменные термины, создаётся лениво
contract/main.tsp             контракт API на TypeSpec, источник истины
contract/openapi.yaml         собирается из main.tsp
server/src/                   сервис на Fastify
server/tests/                 Vitest: модульные и интеграционные
web/src/                      интерфейс на React
e2e/                          Playwright: сквозные сценарии
.cline/skills/                навыки агента
```

Назначение папок:

- `contract`: что и как спрашивает сервис.
- `server`: правила предметной области, включая вычисление слотов.
- `web`: отображение и ввод, без собственных правил предметной области.
- `e2e`: сценарии С1 до С17 из PDR.
- `docs/pdr` и `docs/adr`: почему принято решение, а не как оно реализовано.

## 4. Как запускать

Точный список команд говорит `package.json`. Здесь только то, чего он не выдаст.

```bash
npm run seed                # без него гость видит пустую страницу
npm run dev:server          # окно 1, http://localhost:8000
npm run dev:web             # окно 2, http://localhost:5173
```

Два окна терминала держатся одновременно: сервер и интерфейс развиваются
раздельно. Собранная версия и контейнер идут на 8000, порт меняется переменной
окружения, а не кодом. Сквозные тесты запускаются после сборки.

## 5. Как тестировать

```bash
npm test                    # Vitest: модульные и интеграционные
npm run test:e2e            # Playwright, после npm run build
```

Обязательно к покрытию. Это дословно сценарии PDR:

| Что проверяем | Сценарий |
|---|---|
| Два одновременных запроса на один слот, второй получает отказ | С2 |
| Повторная отмена той же записи отклоняется | С3 |
| Доступ по ссылке-коду, чужой код не открывает встречу | С4 |
| Показ времени в поясе гостя не меняет хранимое время | С5, С15 |
| Время не из сетки слотов вызывает отказ | С12 |
| Пустой или обратный диапазон дат, неверное рабочее окно | С13, С14 |
| Нет такого типа встречи или записи, ответ «не найдено», а не пустой список | С16 |
| Нет часов приёма, гость видит пустую сетку, а не ошибку | С10 |
| Неверные данные гостя, отказ с пояснением что поправить | С11 |
| Две действующие брони на один слот невозможны ни при каких условиях | инвариант из С2 |

Критерий завершения: прогон `npm test` зелёный целиком, каждая строка таблицы
выше закрыта зелёным тестом, а набор маршрутов сервера совпадает
с `contract/openapi.yaml`.

## 6. Порядок работы Design First

1. **PDR.** Что и для кого. Уже есть: `docs/pdr/0001-bronirovanie.md`.
2. **Контракт.** `contract/main.tsp`, из него собирается `contract/openapi.yaml`.
   Новый функционал описывается здесь раньше, чем пишется код. Готово, когда
   пересборка проходит и каждая операция отражает сценарий PDR.
3. **Проверка контракта.** Тест, что сервер отвечает теми же маршрутами. Готово,
   когда лишний и пропущенный маршрут роняют этот тест.
4. **Сервис.** Zod-схемы на входе, обработчики, вычисление слотов, работа с базой.
   Готово, когда неверные данные отклоняются, а бронь вне сетки невозможна.
5. **Тесты.** Модульные и интеграционные. Готово, когда таблица раздела 5
   зелёная целиком.
6. **Интерфейс.** Против контракта, а не против догадок о формате ответа. Готово,
   когда каждое состояние из раздела 5 есть на экране.
7. **Сквозные тесты.** Playwright по главным путям: запись, отказ, отмена. Готово,
   когда эти три пути проходят в браузере без ручных действий.
8. **Контейнер и CI.** Docker и GitHub Actions. Готово, когда `docker compose up`
   поднимает сервис одной командой, а CI зелёный.

Правило: источник истины правится раньше кода, код не выходит вперёд контракта.

## 7. Соглашения по коду

- Тип выводится из схемы Zod через `z.infer`, до `any` не сужается.
- Имена полей в API берутся из контракта; внутри кода TypeScript имена в `camelCase`.
- Дата это строка вида `ГГГГ-ММ-ДД`, время это строка вида `ЧЧ:ММ:СС`. Объект `Date`
  применяется только для вычислений.
- Хранение времени одно общее (UTC), показ считается в поясе смотрящего: перевод
  часов меняет только показ.
- Слоты считаются на лету: чистая функция, расписание и записи приходят в неё
  параметрами.
- Каждый обработчик начинается с `schema.parse`: данные проверяются на границе.
- Ответ об ошибке несёт машиночитаемый код и сообщение на русском языке.
- У записи два состояния: действующая и отменённая. Новая запись создаётся заново.
- Создание брони проходит единственную проверку «свободно» с уникальным ключом
  в базе: параллельные запросы дают одну действующую бронь.
- В русских текстах кавычки «ёлочки», тире заменяем запятой или двоеточием.
- Решение с непонятными последствиями фиксируется ADR в `docs/adr/`.

## 8. Чего делать нельзя

- Подтверждение живёт на экране: гость получает его, ссылку-код и файл календаря.
  Рассылок и напоминаний нет, почта остаётся контактом организатора.
- Пароль один и он у организатора в кабинете. Входа гостя нет, и восстанавливать
  его по адресу почты нечем.
- Встречу отменяют, а не переносят: слот освобождается, новое время бронируют
  заново.
- Расписание целиком описывается днями недели, рабочим окном и шагом, исключений
  в нём нет; перерыв закрывается другим набором дней.
- Слот принадлежит одному гостю: групповых записей не бывает.
- Вовне уходит только файл календаря: внешних календарей, оплаты, SMS и
  мессенджеров в объёме нет.
- Записи живут без ограничения числа и не удаляются, включая отменённые:
  история нужна организатору.
- Кабинет один и организатор в нём один: командных ролей не делаем.
- Прошедшие дни показываются приглушённо и остаются доступны для просмотра.
